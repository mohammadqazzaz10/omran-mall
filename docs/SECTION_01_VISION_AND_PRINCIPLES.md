# القسم 01 — الرؤية العامة والهدف والمبادئ الملزمة

**المراجع الملزمة:** `docs/MASTER_REQUIREMENTS_AR.md` §1 و`docs/MASTER_REQUIREMENTS_EN.md` §1.  
**النطاق:** حوكمة المنتج ومعايير قبوله التي تنطبق على الأقسام الأربعين كافة.  
**القاعدة:** هذا القسم يؤسس قواعد التصميم والتنفيذ والقبول؛ ولا يعني وحده أن الوظائف التشغيلية في الأقسام الأخرى قد نُفذت.

## 1. الرؤية والهدف

إنشاء منصة مؤسسية موحدة لإدارة دورة حياة موظفي عمران مول والعمليات اليومية والإدارية والمالية والتواصل والرقابة عبر الفروع، بدءاً من إنشاء الملف الوظيفي وحتى انتهاء الخدمة. يجب أن تعمل المجالات كوحدات مترابطة ضمن مصدر بيانات موثوق وصلاحيات موحدة وسجل تاريخي قابل للتدقيق.

النظام ليس تطبيق حضور فقط ولا مجموعة شاشات تجريبية. كل وظيفة معلنة يجب أن تكون مدعومة بتدفق عمل حقيقي وبيانات دائمة وواجهات API محمية وواجهة مستخدم مناسبة واختبارات تثبت السلوك.

## 3. ثوابت المنتج العامة

1. العربية هي اللغة الافتراضية مع RTL كامل، والإنجليزية مدعومة مع LTR.
2. العملة JOD، وتخزن المبالغ بدقة ثلاثة منازل عشرية؛ يمنع استخدام floating point للحسابات المالية.
3. المنطقة الزمنية التشغيلية `Asia/Amman`، وتستخدم ساعة الخادم للعمليات الحساسة.
4. PostgreSQL هو مصدر الحقيقة للبيانات الدائمة؛ Redis لا يستبدل السجلات الدائمة.
5. كل API وWebSocket event ومرفق وتقرير يخضع للمصادقة والصلاحية ونطاق البيانات.
6. لا تُفعّل الرسائل الجماعية أو الخصومات أو أي أثر مالي أو نشر إنتاجي قبل الاختبارات والموافقة المطلوبة.
7. لا تستخدم بيانات موظفين حقيقية في التطوير أو الاختبارات.
8. لا يعلن دعم Offline أو Push أو منصة أو تكامل إلا بدليل اختبار يطابق الادعاء.
9. لا يحذف تحديث البيانات الحالية التاريخ الوظيفي أو سجلات التدقيق.
10. لا تمنح صلاحيات عابرة للفروع افتراضياً؛ الوصول متعدد الفروع يتطلب صلاحية صريحة.

## 4. بوابة مراجعة إلزامية لكل تغيير

يجب أن يجيب كل Pull Request عن الآتي، مع توضيح «لا ينطبق» وسببه عند الحاجة:

- ما أرقام الأقسام والمتطلبات التي يحققها التغيير؟
- ما علاقاته بالأقسام السابقة واللاحقة، وما العقود المشتركة التي يعتمد عليها؟
- هل اكتملت طبقات قاعدة البيانات وBackend والواجهة والصلاحيات والتوثيق ذات الصلة؟
- ما الهوية والصلاحية ونطاق الفرع المطلوب؟ وهل تم التحقق منها على الخادم؟
- هل توجد بيانات شخصية أو مالية أو ملفات أو إشعارات؟ وكيف حُميت ودُققت؟
- ما سيناريوهات النجاح والفشل والتزامن وانقطاع الاتصال والتكرار؟
- ما الاختبارات التي شُغلت فعلياً، وما نتيجة CI على commit نفسه؟
- هل تتطلب التغييرات migration أو backup/restore أو rollback؟
- هل تم تحديث مصفوفة التتبع وOpenAPI/ERD والوثائق عند الحاجة؟
- هل يغير التغيير سلوكاً تشغيلياً أو مالياً أو قانونياً يحتاج اعتماد مالك النظام؟
- هل اختُبرت الوظائف السابقة المتأثرة ولم يحدث تراجع فيها؟

## 5. تعريف إنجاز القسم الأول

يُقبل الإطار الحوكمي للقسم الأول عندما:
- تكون الرؤية والنطاق الوظيفي وثوابت المنتج موثقة بالعربية والإنجليزية.
- يكون لكل مبدأ معرف ثابت وضابط تنفيذي ودليل قبول محدد.
- تكون بوابة المراجعة جزءاً من قالب Pull Request.
- ترتبط حالة القسم الأول بمصفوفة الأقسام الأربعين.
- تكون قواعد حماية التوافق وعدم كسر الأقسام السابقة واضحة في دورة التطوير.
- تبقى الفجوات التنفيذية ظاهرة ومصنفة ولا تتحول إلى ادعاء اكتمال.

**حدود الإنجاز:** إتمام هذا القسم يثبت إطار الحوكمة ومعايير التطوير والمراجعة. ولا يثبت وحده أن جميع وظائف المنتج قد نُفذت أو اجتازت القبول؛ يجب إثبات المبادئ عملياً عبر تنفيذ الأقسام التشغيلية واختبارها. لذلك تظل حالة تحقق الرؤية النهائية مرتبطة بإغلاق الأقسام 2–40.
