# القسم 02 — البنية التقنية والهندسية

**المرجع الملزم:** القسم 2 من `docs/MASTER_REQUIREMENTS_AR.md`، مع الالتزام بالقسم 1 وقرارات `docs/ARCHITECTURE_DECISIONS.md`.
**الغرض:** تثبيت معمارية قابلة للتنفيذ والاختبار، ومنع التناقض بين الوثائق والكود، وتحديد ما هو قائم فعلاً وما يزال اعتماداً أو فجوة.
**قاعدة الإثبات:** وجود dependency أو ملف إعداد أو رسم معماري لا يثبت أن الخدمة متكاملة أو جاهزة للإنتاج.

## 1. المعمارية المعتمدة

يعتمد المشروع حالياً **Modular Monolith**: تطبيق NestJS واحد بوحدات مجال مستقلة، وواجهة Flutter متعددة المنصات، وقاعدة PostgreSQL مركزية. لا نقسم النظام إلى microservices قبل وجود حاجة تشغيلية مثبتة؛ حدود الوحدات والعقود الداخلية يجب أن تسمح بالفصل مستقبلاً دون تكرار منطق الأعمال.

طبقات النظام:
1. تطبيقات العميل: Flutter/Dart لتطبيق Android وiOS وFlutter Web، مع واجهات متجاوبة بحسب الدور وحجم الشاشة.
2. واجهة الخدمات: NestJS REST API تحت `/api/v1`، مع DTO validation وOpenAPI/Swagger.
3. الأحداث الحية: Socket.IO/WebSocket للأحداث المصرح بها أثناء اتصال العميل.
4. البيانات الدائمة: PostgreSQL هو مصدر الحقيقة، والمعاملات تنفذ عبر طبقة اتصال مركزية.
5. البيانات المؤقتة والمهام: Redis للاستخدامات المؤقتة والطوابير بعد استكمال تكامل كل مهمة واختبارها؛ لا يحمل السجل الدائم الوحيد لأي عملية.
6. الملفات: مخزن كائنات متوافق مع S3 بروابط موقعة قصيرة العمر عند تنفيذ وحدة الملفات؛ لا تُخزن الملفات الحساسة كروابط عامة.
7. الإشعارات الخارجية: FCM لأجهزة Android والويب المدعوم، وAPNs لـ iOS، مع Web Push للمتصفحات عند استكمال التكامل. WebSocket ليس بديلاً عن Push.
8. التشغيل: Docker/Compose للتطوير والبناء، وCI للتحقق من التغييرات. Render مؤجل إلى بوابة النشر النهائية ولا ينشأ أي مورد إنتاجي ضمن هذا القسم.

## 2. قرارات التنفيذ الفعلية في المستودع

| المجال | القرار المعتمد | ما يثبته المستودع حالياً | الحدود الحالية |
|---|---|---|---|
| تطبيق العميل | Flutter/Dart + Riverpod + GoRouter | `client/` وملف `pubspec.yaml` وملفات Android/iOS/Web | وجود المنصات لا يثبت اختبارها على أجهزة فعلية |
| Backend | NestJS + TypeScript، Modular Monolith | `backend/src/app.module.ts` ووحدات المجال | لا تُنشأ خدمة مستقلة لكل مجال دون قرار ADR |
| API | REST بإصدار `/api/v1` وDTO validation | `main.ts` وSwagger وGlobal ValidationPipe | يجب تحديث OpenAPI مع كل endpoint |
| قاعدة البيانات | PostgreSQL عبر `pg` (node-postgres) | `DatabaseService` وPool ومعاملات صريحة | لا يستخدم المشروع Prisma أو TypeORM حالياً |
| Schema changes | SQL migrations مرقمة وبصمات SHA-256 وقفل advisory | `database/migrations/` وmigration runner | يلزم استمرار اختبار قاعدة فارغة وترقية قاعدة موجودة |
| Cache/Queue | Redis 7 وعميل ioredis عند الحاجة | خدمة Redis في Docker Compose واعتمادية ioredis | لا يُعلن تكامل Queue أو ضمان تسليم قبل وجود worker واختبارات |
| Realtime | Socket.IO عبر NestJS WebSocket Gateway | الاعتماديات ووحدات الأحداث الحالية | يلزم إثبات المصادقة والصلاحية ونطاق الفرع وإعادة الاتصال |
| الملفات | S3-compatible object storage | قرار معماري فقط في هذه النسخة | لا يوجد تكامل تخزين إنتاجي مثبت؛ لا ترفع ملفات حساسة إلى Git |
| Push | FCM + APNs + Web Push | متطلبات وقرار معماري | لا يوجد إثبات توصيل حقيقي عند إغلاق التطبيق |
| الحاويات | Docker image وDocker Compose | `backend/Dockerfile` و`backend/docker-compose.yml` | نجاح البناء لا يعني إعداد بيئة إنتاج |
| CI | Backend وFlutter Web/Android وفحوصات الاختبار | GitHub Actions | iOS device/archive وPush الحقيقي يحتاجان مسار تحقق مستقل |
| الاستضافة | Render خيار الاستضافة النهائي | لا نشر ضمن هذا التغيير | يبقى مؤجلاً إلى اكتمال الأمن والقبول وموافقة المالك |

## 3. عقود التكامل بين الطبقات

- كل طلب محمي يمر عبر المصادقة ثم الصلاحية ثم التحقق من نطاق المورد والفرع على الخادم؛ حراسة المسارات في Flutter لتحسين تجربة الاستخدام وليست حاجزاً أمنياً.
- لا يقبل الخادم `company_id` أو `branch_id` من العميل باعتباره حقيقة موثوقة. يستخرج النطاق من هوية المستخدم وعضوياته، ويُتحقق من ملكية المورد داخل الخدمة والمعاملة.
- تستخدم قاعدة البيانات قيود FK وUNIQUE وCHECK والفهارس المناسبة، مع RLS أو عزل مكافئ مثبت ضمن سياق المعاملة قبل اعتبار عزل الفروع مكتملاً.
- العمليات متعددة الخطوات تستخدم معاملة PostgreSQL واحدة، ويكتب سجل التدقيق ضمن المعاملة نفسها عند الحاجة.
- الوقت الحساس مصدره الخادم؛ تحفظ الطوابع الزمنية كـ `timestamptz` وتعرض حسب `Asia/Amman`.
- المبالغ بالدينار الأردني بدقة ثلاثة منازل وتخزن في `NUMERIC`، ولا تستخدم عمليات floating-point للحساب المالي.
- كل حدث Socket.IO يتحقق من هوية الجلسة والعضوية والصلاحية ونطاق الغرفة عند الاتصال وعند تنفيذ العملية؛ لا يعتمد على اسم الغرفة المرسل من العميل.
- الملفات لا تُعرض إلا بعد تحقق الصلاحية ونطاق الفرع، وتصدر روابط موقعة مؤقتة. لا تستخدم أسماء ملفات أو مسارات يحددها العميل مباشرة على نظام الملفات.
- أي عملية غير متصلة تبقى Pending وغير نهائية حتى تأكيد الخادم، وتحمل مفتاح idempotency وسياسة تعارض. لا تفعّل Offline للعمليات الحساسة قبل اختبار المزامنة.
- Push له سجل تسليم ومحاولات وإزالة token غير الصالح ومنع التكرار. لا يوصف WebSocket بأنه إشعار يعمل والتطبيق مغلق.

## 4. حدود المنصات

- Android: يتطلب بناء Debug/Release واختبار الصلاحيات والإشعارات والروابط العميقة على أجهزة أو محاكيات مناسبة.
- iOS: يتطلب بناء على macOS، وإعداد Bundle ID وSigning وAPNs عبر حساب المالك، واختبار جهاز حقيقي. نجاح Flutter Analyze أو Web لا يثبت جاهزية iOS.
- Web: يتطلب Release build واختبار RTL/LTR والاستجابة وإدارة الجلسة وWeb Push في المتصفحات المدعومة.
- Tablet/Desktop: يجب اختبار تخطيطات واسعة ولوحات الإدارة، لا مجرد تكبير واجهة الهاتف.
- اختلاف قدرات المنصات يعالج عبر واجهات adapters موثقة، ولا يسمح بادعاء ميزة غير مدعومة في منصة معينة.

## 5. متطلبات الأمن والتشغيل

- أسرار التشغيل في متغيرات بيئة/Secret Manager فقط، مع فصل development وstaging وproduction.
- TLS إلزامي خارج localhost، وCORS بقائمة origins محددة، وHelmet وإعدادات الإنتاج الآمنة.
- Health endpoints تميز بين liveness وreadiness؛ readiness يفحص قاعدة البيانات والاعتماديات الإلزامية.
- سجلات منظمة لا تحتوي كلمات مرور أو tokens أو بيانات شخصية غير لازمة.
- migrations قابلة للتدقيق، لا تعدل migration سبق تطبيقها؛ أنشئ migration جديدة.
- Docker يعمل بمستخدم غير root في صورة التشغيل، ويحتوي healthcheck، ولا يضم ملفات البيئة السرية.
- لا تفعيل للإرسال الجماعي أو Push الفعلي أو النشر قبل اختبار التكامل وموافقة المالك وتوفير حسابات المالك.

## 6. بوابة قبول القسم 02

لا يصنف القسم «مكتمل» إلا بعد توفر جميع الأدلة المناسبة:
1. توثيق عربي وإنجليزي متطابق مع الكود وقرارات ADR.
2. نجاح Backend build/format/tests وFlutter analyze/tests وWeb Release وAndroid Debug على commit واحد محدد.
3. إضافة iOS build/signing validation على macOS قبل إعلان دعم إصدار iOS.
4. تطبيق migrations على قاعدة فارغة وترقية قاعدة قائمة دون فقد بيانات، مع اختبار backup/restore.
5. اختبارات تكامل API وWebSocket تثبت المصادقة والصلاحيات ونطاق الفرع.
6. إثبات عمل Redis/Queue وS3 وFCM/APNs/Web Push باختبارات فعلية قبل إعلان أي منها متكاملاً.
7. اختبار RTL/LTR والاستجابة على هاتف ولوحي ومتصفح.
8. تحديث OpenAPI وERD ومصفوفة التتبع، وتسجيل نتائج CI على SHA نفسه.
9. توثيق إعدادات كل بيئة وخطة rollback، دون نشر Render في هذه البوابة.

## 7. الحالة الحالية

**الحالة: جزئي — القرارات الأساسية موثقة وبعض البنية موجودة، لكن تكاملات المنصات والخدمات الخارجية والتحقق التشغيلي ليست مكتملة.**

لا يعلن هذا القسم جاهزاً للإنتاج. الفجوات المثبتة حالياً تشمل: تحقق iOS على macOS وجهاز فعلي، تكامل S3، توصيل Push حقيقي، Queue workers المثبتة، عزل قاعدة البيانات داخل سياق المعاملة، واختبارات تكامل شاملة لكل المنصات.
