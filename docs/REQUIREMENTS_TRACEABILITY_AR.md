## تحديث القسم 02 — البنية التقنية والهندسية

وثائق القسم:
- العربية: `docs/SECTION_02_TECHNICAL_ARCHITECTURE_AR.md`
- English: `docs/SECTION_02_TECHNICAL_ARCHITECTURE_EN.md`

تم توحيد وصف البنية مع الكود الفعلي: Backend بنمط Modular Monolith على NestJS، وPostgreSQL عبر `pg` لا Prisma/TypeORM، وFlutter تحت `client/`، وDocker/Compose وOpenAPI وCI. تم توضيح أن Redis وSocket.IO وS3 وFCM/APNs/Web Push قدرات متفاوتة ولا تعتبر متكاملة لمجرد وجود اعتماديات أو وثائق.

**الحالة: جزئي — القرارات موثقة وبعض البنية موجودة؛ لا تزال اختبارات iOS الفعلية، وتكامل S3 وPush والـ workers، وعزل قاعدة البيانات ضمن المعاملة، واختبارات التكامل متعددة المنصات مطلوبة.**

## تحديث القسم 01 — الرؤية والمبادئ الملزمة

وثائق القسم:
- العربية: `docs/SECTION_01_VISION_AND_PRINCIPLES.md`
- English: `docs/SECTION_01_VISION_AND_PRINCIPLES_EN.md`

يشمل التنفيذ توثيق نطاق الرؤية الوظيفي ذي العشرين مجالاً، وثوابت المنتج، والمبادئ العشرة VSN-01 إلى VSN-10، وضوابطها التنفيذية وأدلة قبولها، وبوابة مراجعة Pull Request التي تفحص الاعتماديات والتوافق واختبارات التراجع عن الوظائف السابقة.

كما عولجت مخالفات Prettier الثلاث الموروثة في ملفات الحضور التي كانت توقف CI قبل build والاختبارات؛ يجب اعتماد نتيجة CI الجديدة على رأس الفرع الحالي قبل الدمج.

**الحالة: جزئي — الإطار الحوكمي منفذ، والتحقق النهائي للمبادئ مستمر.** التوثيق بالعربية والإنجليزية وقالب المراجعة جاهزة للمراجعة. لكن إثبات العزل متعدد الفروع، والإشعارات الفعلية، والعمل دون اتصال، وحماية البيانات، وعدم فقدها، ودعم المنصات يتطلب تنفيذ الأقسام التشغيلية ذات الصلة واختبارها. لا يُغلق القسم الأول باعتباره تحققاً نهائياً للرؤية قبل اكتمال الأقسام 2–40.

## تحديث القسم 03 — الشركة والفروع والهيكل التنظيمي

وثائق القسم:
- العربية: `docs/SECTION_03_COMPANY_BRANCHES_AR.md`
- English: `docs/SECTION_03_COMPANY_BRANCHES_EN.md`

أضيفت واجهة إدارية ثنائية اللغة لعملية النقل، كما مُنح HR_MANAGER صلاحية قراءة دليل الفروع فقط لاختيار المصدر والوجهة دون صلاحية إنشاء/تعديل الفروع. فُعّل `BranchIsolationGuard` على واجهات الهيكل التنظيمي والحضور والاستراحات ذات المسار المحدد بالفرع، إلى جانب PermissionGuard. وأضيفت صلاحية شركة مستقلة لنقل الموظف بين الفروع، تمنح للأدوار العليا والموارد البشرية فقط، ونقطة API تتحقق من انتماء الفرع والقسم والمسمى والمدير إلى الشركة/الفرع المستهدف. يسجل النقل في `employee_history`، وتبقى سجلات الحضور القديمة مرتبطة بفرعها. تُزال إسنادات الأدوار الخاصة بفرع المصدر، وتبقى أدوار الإدارة على مستوى الشركة فعالة، ولا تُنسخ صلاحيات الفرع القديم إلى الفرع الجديد. يرفض النقل مع حضور أو استراحة مفتوحة أو ورديات منشورة مستقبلية أو موظفين تابعين أو مسؤولية إدارة قسم.

**الحالة: جزئي — نُفذت عملية نقل الموظف وضوابطها الأساسية؛ إدارة دورة حياة الفروع، وتغطية كل العلاقات التشغيلية، وعزل PostgreSQL الشامل واختبارات التكامل متعددة الفروع ما زالت مطلوبة.**

## قاعدة التصنيف

- **جزئي:** توجد طبقة أو أكثر من قاعدة البيانات/API/الواجهة/الاختبارات، لكن الوظيفة الكاملة أو ضوابط الإنتاج غير مثبتة.
- **هيكل بيانات فقط:** توجد جداول أو أعمدة في `schema.sql` دون محرك أعمال وواجهات واختبارات قبول متكاملة.
- **غير منفذ:** لم تظهر وحدة تنفيذ فعلية في Backend وFlutter عند فحص شجرة المستودع.
- **غير مثبت:** قد توجد أجزاء، لكن لا يوجد دليل كافٍ على اختبارات تكامل/قبول تغطي المتطلب.

وجود جدول في المخطط أو شاشة شكلية لا يساوي اكتمال الميزة. لا يصنف أي بند «مكتمل» إلا بعد اكتمال قاعدة البيانات والخادم والواجهة والصلاحيات والاختبارات والتوثيق بحسب طبيعة المتطلب.

## نتيجة التدقيق التنفيذي

**النتيجة: المشروع غير مكتمل حالياً، ولا يصح وصفه بأنه جاهز ولم يتبقَّ سوى ربط Render.**

المكونات التنفيذية الظاهرة في شجرة المشروع الحالية:
- الهوية والجلسات والصلاحيات الأساسية.
- إدارة تنظيمية وملفات موظفين عبر API.
- إدارة أولية للمستخدمين والفروع والأدوار والجلسات.
- محرك الاستراحات وواجهاته للموظف والإدارة، وهو قيد طلب دمج PR #19 ولم يكن مدمجاً في `main` وقت التدقيق.
- أساس API وواجهة موظف للحضور والانصراف وطلبات التصحيح على فرع PR #20؛ ما زال CI ومراجعة القبول مطلوبين.

المكونات الغائبة أو غير المكتملة كوحدات Backend/Flutter فعلية عند التدقيق تشمل الورديات، المغادرات، الإجازات، الرواتب، المهام، الإعلانات والرسائل، الإشعارات الفعلية، التقارير، الأصول، التدريب، التوظيف، إنهاء الخدمة، السلامة والطوارئ، والتقييمات/المخالفات/المكافآت.

## خطة الإغلاق التنفيذية

ترتيب التنفيذ لا يعني إسقاط أي متطلب. لا تنتقل الوحدة إلى حالة مكتملة قبل اجتياز Definition of Done.

1. **إغلاق الأساس الأمني والهوية:** RLS أو عزل مكافئ على مستوى قاعدة البيانات، اختبار تسرب بين الفروع والأقسام، استكمال إدارة الأدوار والعضويات والحسابات والأجهزة والاستعادة وMFA، وتدقيق كل endpoint وWebSocket.
2. **إكمال الاستراحات ودمجها:** مراجعة حالات التزامن والحصص والفواصل والمنع والتأخير والصلاحيات والأحداث الحية، ثم CI على رأس الفرع ودمج PR #19 بعد اجتياز بوابة القبول.
3. **التشغيل اليومي:** الحضور والانصراف والتصحيح وQR وGeo-fence والورديات وتبديلها والمغادرات والاستئذانات.
4. **الخدمات والاتصال:** مركز الطلبات والموافقات والإعلانات والرسائل والإشعارات الحقيقية في الخلفية.
5. **الموارد البشرية والمالية:** الإجازات والعطل والأرصدة والرواتب والسلف والبدلات والخصومات والتقييم والمخالفات والمكافآت والتدريب والتوظيف وإنهاء الخدمة.
6. **إدارة الأصول والسلامة:** العهد والمعدات والحوادث والطوارئ.
7. **لوحات وتقارير:** لوحة الموظف، لوحة المشرف، لوحة مدير الفرع، لوحة الإدارة العليا، التقارير والتصدير والبحث والأرشفة.
8. **الاختبارات والقبول:** اختبارات Unit/Integration/E2E/Widget، اختبارات صلاحيات وعزل، ضغط وأداء، استعادة نسخة احتياطية، UAT، مراجعة أمنية، توثيق التشغيل وخطة الرجوع.
9. **Render آخر خطوة:** لا إعداد أو نشر إنتاجي قبل اكتمال البنود السابقة. ربط مفاتيح FCM/APNs ومزود التخزين والبريد/النطاق وقاعدة البيانات يتم عند توفر حسابات المالك، ولا يجوز وضع أسرار حقيقية في Git.
